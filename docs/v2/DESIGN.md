# collectbase v2 — 分层记录文件系统:层即分支(设计)

> **状态:设计中(founding doc)。** v2 是一次**定位转向**。v1 的 engine / worker / sink 三角色——监听上游、增量读、归一成 session、推给 memory system——**整体作废**,不再保留。
>
> v2 的 collectbase 只干一件事:**把智能体的信息记录层做成一个分层文件系统**。最下面是事实层,智能体够不着;上层是它自己的推论,可以反复重写。底层实现是 **Git 分支**,对外接口**也是 Git**——用户和智能体敲的是 `git checkout` / `git commit` / `git log`,collectbase 提供的是让 Git 表现出分层语义的那套东西:分支拓扑 + hook。
>
> 名字仍叫 collectbase(collect = 把智能体积累的东西**收拢**成有结构的一叠),但它现在是一个**工具**,不是一个服务。
>
> v1 设计存档在 [`../v1/`](../v1/),已停止演进。

---

## 0. 一句话

> **给智能体一块它够不着的地板。** 事实放最底层,只读;推论放上层,随便改。层就是 Git 分支,`git checkout layer2` 就是切到"事实 + 笔记"这个视图,`git checkout layer3` 再叠上"结论"。层与层之间**路径不相交**,所以永不冲突、永不覆盖、永不需要合并策略。

```
git checkout beliefs   →   工作树 = facts + notes + beliefs   (只有 beliefs 可写)
git checkout notes     →   工作树 = facts + notes             (只有 notes 可写)
git checkout facts     →   工作树 = facts                     (人 / 采集器可写)
```

没有联合挂载,没有 FUSE,没有 overlay。**Git 本来就在做这件事**——一个分支的工作树就是一个视图,切分支就是切视图。collectbase 只是保证这些分支之间维持着"层"该有的关系。

---

## 1. 为什么要分层

智能体的记忆会腐烂,腐烂的方式很具体:**它把自己的推论当成观测,下一轮基于那个推论再推**。三五轮之后,内容还是自洽的、还是引用得头头是道,只是跟现实脱钩了。这不是模型不够聪明,是它的工作记忆里**观测和推论长得一模一样**——都是文件,都能改,改完看不出区别。

分层就是在文件系统这一层把这条回路切断:

- **事实层**放真正发生过的东西——会话记录、命令输出、外部文档、人写下的约束。谁写它取决于场景(采集器、人、外部同步),但**智能体不写**。
- **上层**放智能体自己的东西:摘要、结构化的记忆、假设、结论。它可以把上一版全推翻重来,这是它该干的事。
- 上层**改不动**下层。不是"不该改",是 Git 层面它够不着——它的提交只能落在自己的分支上。

所以演化是有地板的:无论上层怎么迭代,重新推导的原料永远是那份没被动过的事实。

> 这不是访问控制,是**认知卫生**。目的不是防坏人,是让"我看到的"和"我以为的"在文件系统上是两种东西。

---

## 2. 核心约束:路径全局唯一

**一个路径只属于一层。上层不能占用下层已有的路径,下层也不能新增一个上层已占的路径。**

这条约束是整个设计的地基,它一次性消掉了一大堆东西:

| 不需要的东西 | 为什么不需要 |
|---|---|
| 遮蔽 / override | 同路径根本不会出现在两层 |
| copy-up(写时复制) | 上层想改下层文件?不允许,只能另写一份 |
| whiteout(删除标记) | 上层没有任何手段让下层文件消失 |
| 合并策略 / 冲突解决 | 三方合并的两侧路径集不相交,天然干净 |

Docker 的类比只到"叠"为止——**overlay 那一整套全不要**。合并视图是严格的**不相交并集**。

三个直接后果,都是想要的:

1. **智能体没有"修改"这个动作,只有"追加"。** 它认为下层某条结论错了,不能改那个文件,只能在自己层里另写一份、引用它。修正变成注解而非覆盖:原文永远在,谁在什么时候提出异议是可 diff 的。
2. **删除也跨不了层。** 上层连"假装没看见"都做不到。这比"不可编辑"更强。
3. **merge 永不冲突。** 这才是选 Git 分支的真正理由。不是为了历史和 diff(那是赠品),是因为在路径不相交的前提下,Git 的合并语义刚好退化成一个免费操作。

## 3. 层即分支:拓扑与不变量

层是**有序**的,自下而上。每层一个分支。上层分支通过 merge **真的包含**下层的全部提交:

```
facts     A───B───────────C───────────D          事实层,只增不改
               ╲           ╲           ╲
notes           M1──E───────M2──────────M3       M* = 把 facts 并进来的 merge
                     ╲           ╲        ╲
beliefs               N1──F───────N2───────N3    N* = 把 notes 并进来的 merge
```

`git checkout beliefs` 拿到的工作树 = facts ∪ notes ∪ beliefs,因为那些文件**真的在这个分支的树里**。不是拼出来的视图,是 Git 原生的一次 checkout。

### 四条不变量

- **I1 不相交**:任意两层的路径集无交集(§2)。
- **I2 包含**:`git merge-base --is-ancestor <下层> <上层>` 恒成立。上层分支包含下层的全部历史。
- **I3 单向**:合并只从下往上。上层的提交**永不**进入下层分支——这就是"够不着的地板"在 Git 层面的准确表述。
- **I4 归属稳定**:一个路径一旦被某层引入,永远归那层。层不能相互"过户"路径(想搬家就是下层删、上层加,两次提交,历史里看得见)。

`cb check` 校验这四条。它们被破坏时,不是报警告,是仓库坏了。

---

## 4. 归属:一个路径归哪层

不另立目录前缀规则,**直接从分支树推**:

```
own(L₁) = tree(b₁) 里的全部路径
own(Lᵢ) = tree(bᵢ) \ tree(bᵢ₋₁)        i > 1
```

因为 I2,`tree(bᵢ) ⊇ tree(bᵢ₋₁)`,所以 `own(Lᵢ)` 恰好是"在第 i 层被引入的那些路径"。

实现就是 `git ls-tree -r --name-only <branch>` 做集合差。**规则和事实是同一份数据**,不会出现"登记表说归 A、实际在 B"的不一致。

> **约定而非规则**:实践上把每层放进各自的顶层目录(`facts/` `notes/` `beliefs/`)最省心,不相交一眼可见。但工具**不强制**这个布局——判定始终来自树。你完全可以让 layer2 往 `facts/` 底下塞文件,只要具体路径没被占。是否放开这个自由度,见 §14。

## 5. 拦截:三道闸

同一条规则,三个执行点,越靠前反馈越快,越靠后越可靠:

```
① chmod a-w       写文件的那一刻就 EACCES     ← 最快,给智能体最直白的信号
② pre-commit      git commit 时拒绝            ← 快速反馈,可被 --no-verify 绕过
③ pre-receive     git push 时拒绝              ← 唯一的真相,不可绕(v2 暂不做,见 §13)
```

**本次只做 ① 和 ②。**它们是 UX,不是安全边界——挡的是"智能体不小心越界"和"白费劲干了半天才被拒",挡不住一个铁了心绕过的进程。真正的保证要等服务端。这一点在 §12 里说清楚,不粉饰。

### ① post-checkout:锁住下层

切到 layer i 之后:

```
tree(bᵢ₋₁) 里的每个文件   → chmod a-w      (下层,只读)
own(Lᵢ)    里的每个文件   → chmod u+w      (本层,可写)
```

两件事让这个土办法能用:

- **不产生假 diff。** Git 只记录可执行位(100644 / 100755),不记录写位。644→444、755→555,Git 眼里毫无变化。
- **不妨碍 Git 自己干活。** POSIX 下删除文件要的是父目录的写权限,不是文件本身的。所以 checkout 切走下层文件、`cb sync` 更新下层内容,都不会被 444 挡住。

> 待验证(M2):Git 覆写已存在文件时是先 unlink 再创建,还是可能直接 `open(O_TRUNC)`。若是后者,遇到 444 会失败,需要在 `cb` 包装的 Git 操作里做"解锁 → 操作 → 重新上锁"。这条在 M2 里实测,不靠猜。

### ② pre-commit:双向拦截

当前分支是层分支时(不是就直接放行,普通分支不管):

```
layer  = 当前分支对应的层
staged = git diff --cached --name-only -z --diff-filter=ACDMRT
lower  = tree(b_{layer-1})                    下层已占的全部路径
upper  = ⋃ own(Lⱼ)  for j > layer            上层已占的全部路径

对每个 staged 路径 p:
    p ∈ lower  →  拒绝:「p 属于 <下层名>,只读」
    p ∈ upper  →  拒绝:「p 已被 <上层名> 占用,换个路径」
    否则       →  放行(本层已有 或 全局未占用的新路径)
```

**向下那一半同样重要,不是对称的装饰。** 事实层新增一个已被上层占用的路径,本身不违反"上层别动下层",但它会在往上 merge 的那一刻炸开——而那是最不该出冲突的时刻。所以拦截必须双向,而且规则统一:**任何层新增路径,都要确认全局未被占用**。

另外两个细节:

- **大小写折叠**比对。大小写不敏感的文件系统上,layer1 的 `Facts/a.md` 和 layer3 的 `facts/a.md` 是两个 Git 路径、同一个磁盘文件。按折叠后比对才挡得住。
- **符号链接**不用特判。层 3 里指向层 1 文件的软链,Git 记录的是链接本身;通过它写会撞上 ①。

## 6. 传播:事实层前进,上层跟进

事实层来了新提交,上层要 merge 才看得见。这件事**用户和智能体都不该管**,由 hook 自动做。

```
post-commit  →  cb sync     刚提交的那层,往上逐级推
post-checkout →  cb sync    切过去时顺手补齐
```

`cb sync` 自下而上逐级检查 `git merge-base --is-ancestor`,不满足就合并:

- **目标是当前分支**:普通 `git merge <下层>`,工作树跟着更新(这是对的,你确实需要看到新事实)。
- **目标不是当前分支**:不切分支、不碰工作树,直接在对象库里做:

  ```sh
  tree=$(git merge-tree --write-tree <上层> <下层>)     # 冲突时非零退出
  new=$(git commit-tree $tree -p <上层> -p <下层> -m "cb: sync facts → notes")
  git update-ref refs/heads/<上层> $new
  ```

  需要 Git ≥ 2.38(`merge-tree --write-tree`)。当前环境 2.39.5,可用。

**必须逐级链式推**(facts→notes,再 notes→beliefs),不能 facts 直接跳到 beliefs——那样 I2 在中间那层就断了。

`merge-tree` 报冲突意味着 I1 已经被破坏(有人绕过了 hook)。这时**不做任何自动解决**,直接失败并指出撞了哪个路径:冲突在这个设计里不是待处理的日常,是损坏信号。

## 7. 配置:层定义放在最底层

根目录一个 `collectbase.toml`,顺序即层序,自下而上:

```toml
[[layer]]
name   = "facts"
branch = "layer/facts"

[[layer]]
name   = "notes"
branch = "layer/notes"

[[layer]]
name   = "beliefs"
branch = "layer/beliefs"
```

**这个文件归最底层所有。**于是层的定义本身也是智能体够不着的东西——它不能给自己加一层、不能改层序、不能把事实层从栈里摘掉。同时因为 I2,每个层分支的树里都有这份文件,hook 从 HEAD 直接读即可,没有引导难题(HEAD 上没有它 → 不是层分支 → hook 放行)。

### hook 跟着仓库走

Git 的 hook 默认在 `.git/hooks/`,**不随 clone 传播**。所以:

```sh
git config core.hooksPath .collectbase/hooks
```

hook 脚本本体放在 `.collectbase/hooks/`,由最底层跟踪。这样 hook 是仓库内容的一部分,clone 出来就在;只剩 `git config` 那一行需要 `cb init` 在每个 clone 里跑一次(这是 Git 的安全设计,绕不过,也不该绕)。

hook 脚本本身是一行:

```sh
#!/bin/sh
exec cb hook pre-commit "$@"
```

逻辑全在 `cb` 里,hook 文件不需要随规则演进而改。

## 8. 用起来是什么样

```sh
# 一次性
cb init --layers facts,notes,beliefs
# 建三个分支、写 collectbase.toml、装 hook、配 core.hooksPath

# 事实进来(人 / 采集脚本 / 外部同步)
git checkout facts
cp ~/.claude/projects/…/session.jsonl facts/sessions/2026-08-14-a.jsonl
git add -A && git commit -m "session 2026-08-14-a"
# post-commit 自动把 facts 推进 notes、再推进 beliefs

# 智能体上班
git checkout beliefs
# 工作树里 facts/ notes/ 全在,全是 444;beliefs/ 可写
$EDITOR beliefs/model-of-the-user.md
git add -A && git commit -m "修正:用户偏好 X 而非 Y"

# 它试图动事实
$EDITOR facts/sessions/2026-08-14-a.jsonl   # → EACCES,当场失败
# 就算它 chmod 回来强行改了:
git commit -am "fix"                        # → pre-commit 拒绝,指出该路径属于 facts

# 看某层自己的演化
git log --oneline layer/beliefs
git diff layer/beliefs~5 layer/beliefs -- beliefs/
```

日常动作全是 Git 的。`cb` 只在 init、诊断、和 hook 内部出现。

## 9. CLI 表面

刻意小。Git 是接口,`cb` 不包装 Git 的日常动词。

| 命令 | 干什么 |
|---|---|
| `cb init --layers a,b,c` | 建分支拓扑、写配置、装 hook |
| `cb sync` | 自下而上传播(hook 调它,也可手动) |
| `cb check` | 校验 I1–I4,列出违反项 |
| `cb owner <path>` | 这个路径归哪层 |
| `cb status` | `git status` 的分层版:改动按层分组,越界的标红 |
| `cb layers` | 列出层、分支、各层文件数、当前在哪层 |
| `cb hook <name>` | hook 入口,不给人直接用 |

**没有** `cb commit` / `cb checkout` / `cb log` / `cb diff`。那些就是 `git commit` / `git checkout` / …。多包一层只会让人搞不清哪个是真的。

## 10. 边界(v2 不做什么)

- **不管内容格式。** 层里放什么文件、什么结构、怎么互相引用,是使用者的事。工具只管路径归属和分支拓扑。
- **不做采集。** v1 的 worker 全部作废。事实怎么进事实层——脚本、rsync、人手动 cp——都行,工具不关心。
- **不推给任何下游。** 没有 sink,没有 memory system,没有 HTTP。
- **不做联合挂载 / FUSE。** 视图由 `git checkout` 提供,足够了。
- **不做冲突解决。** 按设计不会有冲突;出现了就是损坏,报错而非修复。
- **不做访问控制。** 本地 hook 是认知卫生,不是安全(见 §12)。

## 11. 里程碑

- **M1 骨架**:`cb init` 建拓扑 + `collectbase.toml` + 归属推导 + `cb check` + `cb owner`。仓库能立起来,不变量能验证。
- **M2 拦截**:`pre-commit` 双向拦截 + `post-checkout` 的 chmod(含 §5 那条 unlink 行为的实测)。地板生效。
- **M3 传播**:`cb sync` + `merge-tree` 离线合并 + `post-commit` 自动触发。事实前进上层自动跟进。
- **M4 手感**:`cb status` / `cb layers`,错误信息说人话(拒绝时告诉它"这个路径归 facts,你要表达异议就在 beliefs/ 里另写一份并引用它")。
- **M5(之后)**:服务端 `pre-receive` + ref 级授权,把 §12 的弱点补上。

## 12. 已知弱点(本地 hook 的真实能力边界)

写在这里是因为它们**不是 bug,是这一版的选择**:

- **`--no-verify` 直接跳过 `pre-commit`。** 这是 Git 的设计,本地 hook 全都可绕。
- **chmod 挡不住铁了心的人。** 智能体自己 `chmod u+w` 就能写。①只是让"不小心"变成"故意"。
- **直接写 `.git/`。** 手搓 object、改 ref,本地 hook 一概看不见。
- **本地 hook 只看当次提交。** 智能体可以先提交一个越界的 commit,再提交一个"改回来"的,`pre-commit` 全程放行——但历史里那次对事实层的改动真实存在。只有服务端 `pre-receive` 拿得到 old→new,能遍历整个 push 里的每个 commit。
- **规则散在每个 clone 里。** 改了拦截逻辑要挨个更新(§7 的 `core.hooksPath` 缓解了大部分,但 `git config` 那一步仍是每个 clone 一次)。

结论没变:**本地负责"别白费劲",服务端负责"事实没被动过"。**M5 之前,这套东西的保证强度是"防手滑,不防对抗"。用在自己驱动的 harness 上够用;要跑不受信任的智能体,等 M5。

---

## 13. 服务端:留着的那条路(M5)

规则同源、一份实现,只换执行点。`pre-receive` 相比本地多三样东西:

1. **ref 级授权**。直接说"`layer/facts` 只有事实写入者能推",而不是逐个路径审查内容。**能授权就别去审查**——审查总有你没想到的绕法,授权是结构性的。
2. **看得见整个 push 的每个 commit**,补上 §12 那条"先越界再改回来"的漏洞。
3. **规则只有一份。**

而且**传播可以挪到服务端**:`post-receive` 里做 §6 的链式 merge,服务器成为"层栈不变量"的唯一维护者,客户端彻底不用管。

成本比想象的低:`pre-receive` 只要接收方是个 bare 仓库就会跑,**本机一个目录就行**,不需要守护进程。要真正的信任边界才需要进程边界——bare 仓库换个 uid + `git-shell`,零长驻进程。

## 14. 待定

- **supersede 语义。** 上层想说"下层那条过时了",在没有覆盖和删除的世界里怎么表达?靠约定的引用(新文件里写明 supersedes 谁),还是读的时候按层高排优先级?不填的话上层会越积越多陈旧结论。M4 之前得有个说法,哪怕只是一条约定。
- **事实层是否 append-only。** 现在只保证"上层动不了",没保证"底层自己不能删"。要不要禁止事实层的删除与修改(只允许新增)?
- **层的增删。** 中途在 1 和 2 之间插一层,意味着上面所有分支要重新挂接。是支持,还是明确不支持、只能重建?
- **归属自由度。** §4 的"任意路径 vs 每层一个顶层目录",要不要把后者从约定升级成强制?强制的话 `cb status` 一眼可读、越界不可能发生;代价是文件按"哪层写的"聚集,而不是按主题。
- **大文件 / submodule。** 事实层可能塞进很大的会话记录。LFS?还是明确说"不管"?
