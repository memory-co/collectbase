# Server:媒体入口与 blob 出口

> `cb serve` 补两个缺口:**blob 有个异地副本**(传到 S3 / OSS / 任意对象存储),**人能把文件拖进来**(网页上传,选一层)。
>
> 主设计见 [`../DESIGN.md`](../DESIGN.md);blob 机制见 [`blob-store.md`](blob-store.md);守卫见 [`cli.md`](cli.md) §4。

---

## 0. 定位:可选的,而且没有特权

两条约束定死,后面所有设计都从它们推:

**① 不跑 server,整套机制照常工作。** 分层、校验、投影、blob 转换全在 git hook 里,零常驻进程。server 只是**便利**:一个媒体入口,一份异地副本。它挂了,仓库不受任何影响。

**② server 没有特权。** 它往仓库里写东西的方式,和人敲 `git commit` 一模一样——落盘、`git add`、`git commit -m "[层名] …"`,然后被同一套 hook 校验。**没有旁路,没有内部 API。** 上传一个属于别的层的路径,它会被 `commit-msg` 拒绝,网页上原样显示那段拒绝信息。

> 这两条不是谦虚,是必要的。只要 server 有一条绕过 hook 的路径,那条路径就是地板上的洞——而 server 恰好是唯一可能被网络访问到的组件。

**它不是 git server。** 不提供 `git clone` / `push`,不做 `pre-receive`。那是主设计 §14 的事,和本篇无关。

---

## 1. 它补的两个缺口

| 缺口 | 出处 | server 怎么补 |
|---|---|---|
| **仓库不再自足**:`git clone` 只带走软链不带字节;`git clean -xdf` 会删光 `blob/` | DESIGN §13 ⑤ | blob 持续上传到对象存储,随时能拉回来 |
| **人往里放大文件很别扭**:得先 `cp` 到工作区、想好放哪个目录、再敲带 `[层名]` 的提交 | — | 网页拖拽,选层,其余自动 |

第二条比看起来重要。事实层的内容常常是**媒体**——截图、录音、PDF、录屏。而命令行恰恰是往仓库里塞媒体最别扭的界面。

## 2. blob 出口

### 后端接口只有四个方法

```
exists(key) -> bool
put(key, local_path)
get(key, local_path)
list(prefix) -> [key]
```

S3 兼容的一份实现就覆盖 S3 / OSS / R2 / MinIO;再加一个 `file://` 后端(就是个目录,等价于 rsync 到 NAS)。**不做多后端抽象层**,四个方法而已。

### 远端布局:纯内容寻址

```
本地   blob/2026/07/23/f1a4f247…ac.png     日期分片,为了能当媒体库浏览
远端   f1/a4/f1a4f247…ac.png               纯 CAS,为了去重
```

本地的日期布局是**浏览用的视图**,远端是**存储**,两者不必一致。远端走 CAS 的理由:同一份内容在不同日子被添加会产生两个本地路径(blob-store §3 的已知代价),远端若照抄就要付两份存储费;而 CAS 天然去重,多个仓库共用一个 bucket 时收益更大。

恢复不需要额外映射:软链的目标里**同时含有日期路径和 sha256**,读出来就知道该取哪个 key、该写回哪个本地路径。

### 什么时候传

- **保证**:周期扫描 `blob/`,把不在远端的传上去。慢一点无所谓,它是兜底。
- **优化**:`post-commit` 顺手 poke 一下 `http://127.0.0.1:<port>/wake`,让 server 立刻扫。**poke 失败必须完全忽略**——server 没起、端口占用、超时,一律不能让提交失败。

上传是**幂等**的:key 是内容哈希,`exists` 为真就跳过。本地存一份"已上传的 sha"缓存加速,但**它是缓存不是状态**,删了只是下次多扫一遍。

### 三条规矩

1. **对象写一次就不再改。** key 是内容哈希,同 key 必然同内容,永不覆盖。建议 bucket 开版本控制或 WORM 策略——**能写这个 bucket 的人就能替换事实层的截图**,这是 DESIGN §13 ② 那个洞在远端的镜像。
2. **server 永不删远端对象。** 本地 `cb blob gc` 按本仓库的活集删本地文件,而远端可能被别的 clone 引用。远端清理要另外的、更保守的流程(跨所有已知仓库取并集),不在 server 职责内。
3. **上传失败不阻塞任何东西。** 记日志、下轮重试。

### 反向:补齐缺失

`clone` 之后、或 `git clean -xdf` 之后,本地 `blob/` 是空的。server 启动时对照活集(`git rev-list --all` 里所有 `120000` 条目)拉回缺失的部分,写盘前**先验 sha256**,已存在且哈希正确的跳过,已存在但哈希不对的**报错而不是覆盖**——那是 `cb check` I5 要人看的现场。

## 3. Web 上传页

### 流程

```
浏览器拖入文件 + 选层 + 填目标目录(可留空)
        ↓
server 落盘到工作区                    inbox/2026-08-14/screen.png
        ↓
git add <精确路径>                     ← 不是 git add -A
git commit -- <精确路径> -m "[facts] 上传 3 个文件"
        ↓
        pre-commit    二进制转 blob + 软链
        commit-msg    三条校验
        post-commit   投影 + 重算
        ref 守卫      白名单 + 归属
        ↓
成功 → 页面显示提交 sha;失败 → 页面原样显示 hook 的拒绝信息
```

**层的下拉选项从写入面的 `layers` 文件读**,不另存一份。

### 三个必须做对的地方

**① 绝不能 `git add -A`。**

工作区可能同时有人(或智能体)在干活,`-A` 会把他们没提交完的东西一起卷进这次上传的提交里。必须 `git add` 精确路径,并用**部分提交** `git commit -- <路径>`。

部分提交在 hook 下的行为已经实测过([`exp-hook.sh`](exp-hook.sh)):钩子拿到的是临时索引 `next-index-*.lock`,改动对本次提交有效,但**主索引里其他已暂存路径仍留着转换前的条目**,要靠 `post-commit` 补。这条对 server 尤其要紧,因为它天生就在"别人也在用这个工作区"的场景里。

**② 拿锁。**

写入面只有一条,提交必须串行(DESIGN §13 ③)。server 和 hook 用同一把锁。拿不到锁时页面显示"正在等待另一个提交完成",别让人以为卡死。

**③ 目标路径冲突要给人话。**

上传到一个已被别层占用的路径,`commit-msg` 会拒。页面要把那段信息原样显示出来,并给出改路径的建议——理由和 [`cli.md`](cli.md) §6 一样:**拒绝信息是这个系统唯一会教人规矩的地方。**

### 工作区共用的问题

server 需要一个 checkout 在写入面的工作区来暂存文件。默认就用**现有的那一个**——简单,而且有了 ① 和 ② 之后不会伤到别人,代价是上传过程中那几个文件会短暂出现在别人的 `git status` 里。

想彻底不打扰,理论上可以给 server 开一个独立 worktree,但**同一分支不能在两个 worktree 里同时 checkout**,只能用 `git worktree add --detach`,然后自己 `update-ref` 推进写入面。那样 hook 的"当前分支是不是写入面"判断会失效(HEAD 是游离的),需要额外的识别方式。**这条路先不走**,记在 §6。

### 绑定与认证

**默认只听 `127.0.0.1`。**

这个页面能往事实层写东西——那是整套设计里信任度最高的位置。一个开在 `0.0.0.0` 上的无认证上传口,等于把地板拆了。所以:**不配置 token 就拒绝绑定非回环地址**,启动时直接报错,不给"我先跑起来再说"的机会。

## 4. 页面上还该有什么

上传是主体,另外两块几乎白送:

- **最近提交**,按层标注(`git log --oneline stack/<最长>` 已经自带 `[层名]`)。人能一眼看到自己刚传的东西落在哪层。
- **blob 同步状态**:活集多少、本地有多少、远端有多少、待上传多少。`cb check` I5 的网页版。

不做别的。这不是一个 git 网页界面。

## 5. 配置

server 的配置**不进仓库**——它是机器级的,而且含凭证:

```toml
# ~/.config/collectbase/server.toml   或 --flag / 环境变量
repo = "/home/me/notes"
bind = "127.0.0.1:8787"
token = ""                    # 绑定非回环地址时必填

[blob_store]
kind      = "s3"              # s3 | file
endpoint  = "https://oss-cn-hangzhou.aliyuncs.com"
bucket    = "my-collectbase"
prefix    = "blob/"
access_key_id     = "…"
access_key_secret = "…"
scan_interval = "5m"
```

仓库里的 `.collectbase/config.toml` 只放**与仓库有关**的可调项(blob 阈值、`force_in` / `force_out`)。两者不混。

## 6. 里程碑

排在主设计 M4(blob)之后:

- **S1 出口** — 后端四方法 + S3 实现 + 周期扫描上传 + 启动时补齐缺失。命令行先行,不带网页。
- **S2 入口** — 上传页:拖拽、选层、目标目录、精确路径的部分提交、锁、拒绝信息透传。
- **S3 观测** — 最近提交、blob 同步状态。
- **S4** — `post-commit` 的 poke;`file://` 后端。

## 7. 待定

- **独立 worktree。** §3 那条"detached + 自己 update-ref"的路,以及 hook 怎么识别"这是 server 在写入面上干活"。
- **上传时的层权限。** 单机单人不需要;一旦配 token 对外开放,要不要区分"谁能写事实层"?
- **超大文件的上传形态。** 浏览器直传对象存储(预签名 URL)再把软链提交进来,还是老老实实走 server 落盘?前者省一次中转,但 server 就得先知道 sha256 才能给 key,而 sha256 要客户端算。
- **多仓库共用一个 bucket。** CAS 布局天然支持,但远端 GC 的活集就得跨仓库取并集——谁来维护那份清单。
- **断点续传 / 大对象分片。** 录屏动辄几百 MB。
