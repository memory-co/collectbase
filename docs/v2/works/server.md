# Server:媒体入口与 blob 出口

> `cb serve` 补两个缺口:**blob 有个异地副本**(传到 S3 / OSS / 任意对象存储),**人有个能用的界面**(一个分层文件管理器:浏览、预览、下载、上传)。
>
> 主设计见 [`../DESIGN.md`](../DESIGN.md);blob 机制见 [`blob-store.md`](blob-store.md);守卫见 [`cli.md`](cli.md) §4。

---

## 0. 定位:可选的,而且没有特权

两条约束定死,后面所有设计都从它们推:

**① 不跑 server,整套机制照常工作。** 分层、校验、投影、blob 转换全在 git hook 里,零常驻进程。server 只是**便利**:一个媒体入口,一份异地副本。它挂了,仓库不受任何影响。

**② server 没有特权。** 它写进去的每个提交,都要通过和别人完全相同的那道闸——`reference-transaction` 的白名单与归属检查([`cli.md`](cli.md) §4)。**没有旁路,没有内部 API。** 往别层占用的路径上传,事务被拒,网页原样显示那段拒绝信息。

> 这两条不是谦虚,是必要的。只要 server 有一条绕过 hook 的路径,那条路径就是地板上的洞——而 server 恰好是唯一可能被网络访问到的组件。

**它不是 git server。** 不提供 `git clone` / `push`,不做 `pre-receive`。那是主设计 §14 的事,和本篇无关。

---

## 1. 它补的两个缺口

| 缺口 | 出处 | server 怎么补 |
|---|---|---|
| **仓库不再自足**:`git clone` 只带走软链不带字节;`git clean -xdf` 会删光 `blob/` | DESIGN §13 ⑤ | blob 持续上传到对象存储,随时能拉回来 |
| **媒体没有界面**:命令行看不了图、听不了音、翻不了 PDF,而事实层里恰恰全是这些 | — | 一个分层文件管理器 |

第二条比看起来重要。事实层的内容常常是**媒体**——截图、录音、PDF、录屏。命令行是往仓库里塞媒体、以及事后翻找媒体最别扭的界面,而 blob 的日期分片布局([`blob-store.md`](blob-store.md) §3)本来就是奔着"能当媒体库浏览"去的,只差一个界面把它兑现。

## 2. blob 出口

### 后端接口只有四个方法

```
exists(key) -> bool
put(key, local_path)
get(key, local_path)
list(prefix) -> [key]
```

S3 兼容的一份实现就覆盖 S3 / OSS / R2 / MinIO;再加一个 `file://` 后端(就是个目录,等价于 rsync 到 NAS)。**不做多后端抽象层**,四个方法而已。

### 远端布局:纯内容寻址

```
本地   blob/2026/07/23/f1a4f247…ac.png     日期分片,为了能当媒体库浏览
远端   f1/a4/f1a4f247…ac.png               纯 CAS,为了去重
```

本地的日期布局是**浏览用的视图**,远端是**存储**,两者不必一致。远端走 CAS 的理由:同一份内容在不同日子被添加会产生两个本地路径(blob-store §3 的已知代价),远端若照抄就要付两份存储费;而 CAS 天然去重,多个仓库共用一个 bucket 时收益更大。

恢复不需要额外映射:软链的目标里**同时含有日期路径和 sha256**,读出来就知道该取哪个 key、该写回哪个本地路径。

### 什么时候传

- **保证**:周期扫描 `blob/`,把不在远端的传上去。慢一点无所谓,它是兜底。
- **优化**:`post-commit` 顺手 poke 一下 `http://127.0.0.1:<port>/wake`,让 server 立刻扫。**poke 失败必须完全忽略**——server 没起、端口占用、超时,一律不能让提交失败。

上传是**幂等**的:key 是内容哈希,`exists` 为真就跳过。本地存一份"已上传的 sha"缓存加速,但**它是缓存不是状态**,删了只是下次多扫一遍。

### 三条规矩

1. **对象写一次就不再改。** key 是内容哈希,同 key 必然同内容,永不覆盖。建议 bucket 开版本控制或 WORM 策略——**能写这个 bucket 的人就能替换事实层的截图**,这是 DESIGN §13 ② 那个洞在远端的镜像。
2. **server 永不删远端对象。** 本地 `cb blob gc` 按本仓库的活集删本地文件,而远端可能被别的 clone 引用。远端清理要另外的、更保守的流程(跨所有已知仓库取并集),不在 server 职责内。
3. **上传失败不阻塞任何东西。** 记日志、下轮重试。

### 反向:补齐缺失

`clone` 之后、或 `git clean -xdf` 之后,本地 `blob/` 是空的。server 启动时对照活集(`git rev-list --all` 里所有 `120000` 条目)拉回缺失的部分,写盘前**先验 sha256**,已存在且哈希正确的跳过,已存在但哈希不对的**报错而不是覆盖**——那是 `cb check` I5 要人看的现场。

## 3. 网页:一个分层文件管理器

不是"上传表单",是**文件管理器**:浏览、预览、下载、上传、删除。分层是它唯一特别的地方。

```
┌─ 层视图: [ 全部 ▾ ] facts · notes · beliefs ────────────────┐
│                                                              │
│  project/                                                    │
│    api.md                        facts    2.1 KB   08-14     │
│    api-notes.md                  notes    5.7 KB   08-13     │
│    api-belief.md                 beliefs  1.2 KB   08-14     │
│    log/                                                      │
│      2026-08-14.jsonl            facts    340 KB   08-14     │
│      screen.png                  facts     5 MB    08-14  ▣  │
│                                                              │
│  [ 拖拽文件到这里上传 → 当前层视图 ]                          │
└──────────────────────────────────────────────────────────────┘
```

### 分层带来的四件事

- **层视图切换**。选 `facts` 就只看事实层的文件,选"全部"就是完整堆叠视图。这就是 `git checkout layer/facts` 和 `git checkout stack/<最长>` 的网页版,不用切分支。
- **每个文件标着归属层**。归属表本来就是现成的(`layer/*` 的树),这一列白送,而且是这个文件管理器最有信息量的一列——**它把"这是观测还是推论"变成了一个可见的属性**。
- **软链完全透明**。`▣` 那个是 blob:点开预览图片,点下载得到原始字节。用户看不到 `blob/2026/07/23/f1a4f2….png` 这层间接,也不需要知道。本地缺这个 blob 就从对象存储拉(§2)。
- **上传的目标层 = 当前层视图。** 不用额外的下拉框——你在看哪一层,就往哪一层传。看"全部"时才需要选。

### 增删改都走同一套规则

| 动作 | 结果 |
|---|---|
| 上传到当前层 | 一个 `[层名] …` 提交 |
| 删除自己层的文件 | 合法,一个 `[层名] …` 提交 |
| 删除 / 改名下层的文件 | **被拒**,页面显示"这个文件属于 `[facts]`,是只读的" |
| 上传到已被别层占用的路径 | **被拒**,提示换个路径 |

页面不需要自己实现任何一条规则,它只是把 hook 的拒绝信息原样显示出来。

### 实现:直接操作对象库,没有工作区

文件管理器不需要暂存区,所以 server 也不需要工作区:

```
浏览   git ls-tree -r <层视图对应的分支>
预览/下载  120000 → 读 blob/(缺了就从对象存储拉);其余 → git cat-file blob
上传   算 sha → 二进制则写进 blob/ 并造软链条目,文本则 hash-object -w
       用写入面的树 + 这几个条目造新树 → commit-tree → update-ref
```

于是**上一版里那个"server 和智能体抢工作区"的问题整个消失了**,`git add`、部分提交、暂存区语义也全都不需要——那是我把网页当成 git 客户端来设计时才有的问题。

两个由此产生的真约束:

**① blob 转换必须是库函数,不能只活在 hook 里。**

server 走 plumbing,`pre-commit` 不会触发,所以转换得自己做。这不是特权旁路——它做完之后 `update-ref` 照样撞上 `reference-transaction`,白名单会检查它有没有老老实实转换([`cli.md`](cli.md) §4)。但**转换逻辑必须和 hook 共用同一份实现**,理由和二进制判据一样:两份实现迟早不一致,而不一致的表现是"server 传上去的东西被守卫拒了",极难排查。

**② 如果有工作区正 checkout 在写入面上,要把那几个路径同步过去。**

`update-ref` 推进分支之后,那个工作区的 HEAD 跟着动了,但磁盘上没有新文件——`git status` 会把它们显示成**已删除**。所以 server 在 `update-ref` 之后,要把这次涉及的**那几个精确路径**写进工作区并更新索引条目。

这不是"暂存",是把别人的视图补齐。而且对 harness 场景这是想要的:智能体就坐在那个工作区里,你刚传进去的事实它下一秒就该看得见。

### 绑定与认证

**默认只听 `127.0.0.1`。**

这个页面能往事实层写东西——那是整套设计里信任度最高的位置。一个开在 `0.0.0.0` 上的无认证上传口,等于把地板拆了。所以:**不配置 token 就拒绝绑定非回环地址**,启动时直接报错,不给"我先跑起来再说"的机会。

## 4. 页面上还该有什么

文件管理器是主体,另外两块几乎白送:

- **最近提交**,按层标注(`git log --oneline stack/<最长>` 已经自带 `[层名]`)。
- **blob 同步状态**:活集多少、本地多少、远端多少、待上传多少。`cb check` I5 的网页版。

不做别的。这不是一个 git 网页界面——**没有分支、没有 diff、没有历史图**。要那些的人手边就有 git。

## 5. 配置

server 的配置**不进仓库**——它是机器级的,而且含凭证:

```toml
# ~/.config/collectbase/server.toml   或 --flag / 环境变量
repo = "/home/me/notes"
bind = "127.0.0.1:8787"
token = ""                    # 绑定非回环地址时必填

[blob_store]
kind      = "s3"              # s3 | file
endpoint  = "https://oss-cn-hangzhou.aliyuncs.com"
bucket    = "my-collectbase"
prefix    = "blob/"
access_key_id     = "…"
access_key_secret = "…"
scan_interval = "5m"
```

仓库里的 `.collectbase/config.toml` 只放**与仓库有关**的可调项(blob 阈值、`force_in` / `force_out`)。两者不混。

## 6. 里程碑

排在主设计 M4(blob)之后:

- **S1 出口** — 后端四方法 + S3 实现 + 周期扫描上传 + 启动时补齐缺失。命令行先行,不带网页。
- **S2 浏览** — 层视图切换、按层标注的文件列表、预览、下载(blob 间接透明)。只读,先把"看得见"做出来。
- **S3 写入** — 上传 / 删除 / 改名,plumbing 造提交,工作区路径同步,拒绝信息透传。
- **S4** — `post-commit` 的 poke;`file://` 后端。

## 7. 待定

- **上传时的层权限。** 单机单人不需要;一旦配 token 对外开放,要不要区分"谁能写事实层"?
- **超大文件的上传形态。** 浏览器直传对象存储(预签名 URL)再把软链提交进来,还是老老实实走 server 落盘?前者省一次中转,但 server 得先知道 sha256 才能给 key,而 sha256 要客户端算。
- **并发写入。** 没有工作区之后,server 走 `update-ref`,守卫的 FF 检查天然挡住了并发丢失(第二个写入者的 old 已经过期,事务被拒)。要不要因此干脆去掉提交锁,靠"被拒就重试"?比锁简单,但重试逻辑要写对。
- **多仓库共用一个 bucket。** CAS 布局天然支持,但远端 GC 的活集就得跨仓库取并集——谁来维护那份清单。
- **断点续传 / 大对象分片。** 录屏动辄几百 MB。
